1. ABSTRACT & INTRODUCTION
================================================================================

FestFlow is a cross-platform mobile application built with Flutter and Firebase
designed to streamline the end-to-end management of college festivals, cultural
events, and organizational gatherings.

The platform introduces a role-based access control (RBAC) system with three
distinct user tiers:

  • LEADER  — The event creator and administrator. Has full control over event
               details, sub-event creation, member invitations, guest approval
               workflows, analytics dashboards, and QR code sharing.

  • MEMBER  — A trusted collaborator invited by the Leader. Can view event
               details, manage assigned sub-events, view analytics, and
               communicate via integrated chat.

  • GUEST   — An external attendee who discovers events via QR scanning or
               browsing the public event list. Must complete a Google Forms-
               style questionnaire (if the event is private) before being
               granted access to sub-event listings and dashboards.

The application solves several key problems:
  - Manual event coordination via WhatsApp/email is error-prone
  - No centralized dashboard for tracking sub-events and attendees
  - Guest registration is typically handled via third-party tools
  - Real-time communication between organizers is fragmented

Key Features:
  ✓ Google Sign-In authentication (OAuth 2.0)
  ✓ Multi-step event creation wizard with location services
  ✓ QR code generation, sharing (WhatsApp, AirDrop, etc.), and scanning
  ✓ Google Forms-style questionnaire builder for guest screening
  ✓ Real-time Firestore-powered notifications
  ✓ AI-powered event analytics via Google Gemini API
  ✓ Online/Offline presence tracking with WidgetsBindingObserver
  ✓ Emergency SOS dialer for guest safety
  ✓ Role-based floating action menus
  ✓ CSV export capabilities for analytics data

4. FIRESTORE DATABASE SCHEMA
================================================================================

The Firestore database is organized into three root-level collections:

────────────────────────────────────────
COLLECTION: leader/{email}
────────────────────────────────────────
Purpose: Stores leader profile and their created events.
Document ID: Leader's email address (e.g., kotojupreetham@gmail.com)

Fields:
  email       : String    — Leader's email address
  username    : String    — Display name
  uid         : String    — Firebase Auth UID
  createdAt   : Timestamp — Account creation timestamp

Sub-collection: leader/{email}/events/{eventCode}
  Contains the event creation data submitted during the 4-step signup wizard.
  Fields include: title, description, location, date, type (public/private),
  amount, image URL, isApproved, timestamp, createdBy, createdByID.

────────────────────────────────────────
COLLECTION: users/{email}
────────────────────────────────────────
Purpose: Stores member and guest profiles.
Document ID: User's email address

Fields:
  email       : String    — User's email
  username    : String    — Display name
  uid         : String    — Firebase Auth UID
  isOnline    : Boolean   — Online/offline presence status
  createdAt   : Timestamp — Account creation timestamp

Sub-collection: users/{email}/events/{eventCode}
  Tracks which events this user has joined and their role.
  Fields:
    role       : String    — "member" or "guest"
    eventCode  : String    — The event code
    eventTitle : String    — Cached event title
    joinedAt   : Timestamp — When the user joined
    isApproved : Boolean   — (Guests only) Whether approved by leader

Sub-collection: users/{email}/notifications/{notificationId}
  Real-time notification feed for the user.
  Fields:
    title      : String    — Notification title
    subtitle   : String    — Notification body text
    timestamp  : Timestamp — When the notification was created

────────────────────────────────────────
COLLECTION: events/{eventCode}
────────────────────────────────────────
Purpose: The master event document. Central hub for all event data.
Document ID: The unique event code (e.g., "COLLE-12345")

Top-level Fields (Map fields):
  details     : Map       — Contains all event metadata (title, description,
                             location, date, type, amount, image, etc.)
  leader      : Map       — Contains leader profile data (email, username, uid,
                             isOnline)
  createdAt   : Timestamp — Event creation timestamp
  isApproved  : Boolean   — Whether the event is approved and live
  signAt      : Timestamp — Last sign-in timestamp

Sub-collection: events/{eventCode}/member/{email}
  Each document represents an invited or joined member.
  Fields:
    email      : String
    username   : String
    uid        : String
    isJoined   : Boolean   — Whether the member accepted the invitation
    isOnline   : Boolean   — Presence status
    profileImage: String   — URL to profile photo

Sub-collection: events/{eventCode}/guest/{email}
  Each document represents a registered guest.
  Fields:
    email      : String
    username   : String
    uid        : String
    joinedAt   : Timestamp
    profileImage: String

Sub-collection: events/{eventCode}/Guest/{email}
  (Note: Capital "G" — legacy collection used during initial guest signup)
  Same structure as guest/{email}.

Sub-collection: events/{eventCode}/sub-events/{subEventId}
  Each document represents a sub-event within the parent event.
  Fields:
    title       : String
    description : String
    date        : Timestamp
    time        : String
    location    : String
    type        : String    — Category of sub-event
    members     : List      — Assigned member emails
    createdAt   : Timestamp

Sub-collection: events/{eventCode}/guestQuestions/{questionId}
  Stores the Google Forms-style questionnaire for private events.
  Fields:
    question    : String    — The question text
    type        : String    — short_answer, paragraph, multiple_choice,
                               checkbox, or dropdown
    options     : List      — Answer options (for MCQ/checkbox/dropdown)
    isRequired  : Boolean   — Whether the question must be answered
    order       : int       — Display order in the form
    createdAt   : Timestamp

Sub-collection: events/{eventCode}/chat/{messageId}
  Real-time chat messages between leader and members.

Sub-collection: events/{eventCode}/notification/{notificationId}
  Event-level notifications (broadcast to all participants).

Sub-collection: events/{eventCode}/permissions/{permissionId}
  Role-based permission grants (e.g., member can manage guests).

INITIALIZATION PATTERN:
  When a new event is created, the following "init" documents are created
  as placeholders in each sub-collection to ensure they appear in the
  Firestore console:
    events/{code}/member/init       → {}
    events/{code}/guest/init        → {}
    events/{code}/Guest/init        → {}
    events/{code}/sub-events/init   → {}
    events/{code}/chat/init         → {}
    events/{code}/notification/init → {}
    events/{code}/permissions/init  → {}

  All queries throughout the app use .where((doc) => doc.id != "init")
  to exclude these placeholder documents from results.

PHASE 1: HOME SECTION
================================================================================
This section covers the entry point of the application, the splash/routing
screen, role selection, authentication, event creation, and shared services.


────────────────────────────────────────────────────────────────────────────────
FILE: lib/main.dart
────────────────────────────────────────────────────────────────────────────────
Type       : Application Entry Point
Lines      : 29
Imports    : flutter/material.dart, firebase_core, firebase_options.dart,
             face_page.dart
Connects To: face_page.dart (sets it as the home widget)

PURPOSE:
  This is the very first file executed when FestFlow launches. It performs
  two critical tasks before any UI is rendered:

  1. WidgetsFlutterBinding.ensureInitialized() — Guarantees the Flutter engine
     is fully initialized before making asynchronous calls. Without this, the
     Firebase.initializeApp() call would crash.

  2. Firebase.initializeApp() — Loads the Firebase configuration from
     firebase_options.dart (auto-generated by FlutterFire CLI). This must
     complete before ANY Firebase service (Auth, Firestore, Storage) can be
     used anywhere in the app.

  After initialization, it creates a MaterialApp with:
    - debugShowCheckedModeBanner: false (removes the debug banner)
    - title: 'FestFlow'
    - theme: ThemeData(primarySwatch: Colors.indigo) — the global color scheme
    - home: FacePage() — the splash/routing screen

BACKEND: No direct Firestore interaction. Purely initialization.
FRONTEND: Creates the root MaterialApp widget tree.


────────────────────────────────────────────────────────────────────────────────
FILE: lib/global.dart
────────────────────────────────────────────────────────────────────────────────
Type       : Global State Container
Lines      : 5
Imports    : None
Connects To: Every dashboard (Leader, Member, Guest), all services

PURPOSE:
  Contains a single static class GlobalState with one static variable:

    static String? activeEventCode;

  This variable is the backbone of the entire application. It stores the
  currently active event code that the user is interacting with. It is set
  during login (face_page.dart) or during event creation (host_zone.dart)
  and is read by every dashboard to fetch event-specific data from Firestore.

  Without this variable, dashboards would not know which event to query.
  It persists across widget rebuilds because it is a static field.

  The variable is cleared (set to null) during logout to prevent stale data
  from leaking between sessions.

PATTERN: Singleton-style global state. No dependency injection framework
         (Provider, Riverpod, Bloc) is used — this is intentional for
         simplicity in a project of this scope.

────────────────────────────────────────────────────────────────────────────────
FILE: lib/home/face_page.dart
────────────────────────────────────────────────────────────────────────────────
Type       : Splash Screen + Auto-Login Router
Lines      : 203
Imports    : firebase_auth, cloud_firestore, google_sign_in, home_page.dart,
             leader_dashboard.dart, member_dashboard.dart, guest_dashboard.dart,
             all_event_list.dart, loading_bar.dart, logo_with_name.dart
Connects To: HomePage, LeaderDashboard, MemberDashboard, GuestDashboard,
             AllEventList
Firestore  : Reads users/{email}/events, events/{eventCode}

PURPOSE:
  The first screen users see — a branded splash screen with "FestFlow" text,
  tagline "The Streamlined Way to Manage Events", and a loading spinner.

  While the splash is displayed, _checkAutoLogin() runs in the background:

  AUTO-LOGIN ALGORITHM:
    1. Check if FirebaseAuth has a cached current user (user from last session)
    2. If no user -> navigate to HomePage (role selection)
    3. If user exists -> query users/{email}/events to find their first event
    4. Extract the role from the event document:
       - "leader" -> Check if events/{code}.isApproved == true -> LeaderDashboard

PURPOSE:
  This is the command center of the entire FestFlow application. When a Leader
  logs in, this is the first screen they see. It is a StatefulWidget that
  implements the WidgetsBindingObserver mixin for online/offline presence
  tracking.

STATE VARIABLES:
  - _menuOpen (bool)         — Controls floating menu visibility
  - eventCode (String?)      — The active event code from GlobalState
  - eventDetails (Map?)      — Event metadata fetched from Firestore
  - isLoading (bool)         — Loading state flag
  - isOnline (bool)          — Local online presence indicator
  - _user (User?)            — Current Firebase Auth user
  - totalSubEvents (int)     — Count of sub-events
  - totalMembers (int)       — Count of joined members
  - totalGuests (int)        — Count of registered guests

LIFECYCLE MANAGEMENT:
  initState():
    1. Adds WidgetsBindingObserver to track app lifecycle
    2. Calls fetchEventCode() to load event data
    3. Calls _setOnlineStatus(true) to mark the leader as online

  dispose():
    1. Removes WidgetsBindingObserver
    2. Calls _setOnlineStatus(false) to mark offline

  didChangeAppLifecycleState(AppLifecycleState state):
    - AppLifecycleState.resumed  -> _setOnlineStatus(true)
    - AppLifecycleState.paused   -> _setOnlineStatus(false)
    - AppLifecycleState.detached -> _setOnlineStatus(false)

ONLINE STATUS METHOD (_setOnlineStatus):
  Updates TWO Firestore documents simultaneously:
    1. users/{email}.isOnline = true/false
    2. events/{code}/leader/{email}.isOnline = true/false
  Also calls setState() to update the local green/grey dot indicator.

DATA FETCHING:
  fetchEventCode():
    1. Gets current user from FirebaseAuth
    2. Tries GlobalState.activeEventCode first
    3. If null -> FALLBACK: queries users/{email}/events to find event code
    4. Sets GlobalState.activeEventCode if found via fallback
    5. Calls fetchEventDetails() and fetchStats()

  fetchEventDetails(String code):
    1. Reads events/{code} from Firestore
    2. Extracts the "details" map field
    3. Sets eventDetails state variable

  fetchStats():
    1. Counts sub-events (excluding "init" docs)
    2. Counts members where isJoined == true
    3. Counts guests (excluding "init" docs)
    4. Updates totalSubEvents, totalMembers, totalGuests

UI LAYOUT:
  AppBar:
    - Title: "Leader Dashboard"
    - Actions (right side):
      a. Online indicator (green/grey CircleAvatar + "Online"/"Offline" text)
      b. QR code button (opens QRViewerDialog)
      c. Settings button (navigates to SettingsPage)

  Body (SingleChildScrollView):
    - Event image (with network error fallback)
    - Event title (bold, 24px)
    - Event details card (dynamically renders all fields except restricted ones)
    - StatsWidget (3 stats: Sub-Events, Members, Guests)

  BottomAppBar:
    - Profile button (navigates to ProfileScreen)
    - Notification button (navigates to NotificationScreen)

  FloatingActionButton:
    - Toggles FloatingMenu visibility
    - Icon changes between add (+) and close (x)

  FloatingMenu (overlay):
    - Blurred background with positioned action buttons
    - Sub-events, Members, Guests, Analytics, Chat, Settings buttons

BACKEND SUMMARY:
  Reads: events/{code}, events/{code}/sub-events, /member, /guest
  Writes: users/{email}.isOnline, events/{code}/leader/{email}.isOnline

FRONTEND SUMMARY:
  Widget tree: Scaffold -> Stack -> [ScrollView, FloatingMenu]

5.1 ARCHITECTURE: Model-View-Controller (MVC) with Firebase BaaS
─────────────────────────────────────────────────────────────────

FestFlow follows a modified MVC architecture adapted for Flutter:

  MODEL LAYER (Data):
    - GlobalState (global.dart) — in-memory state container
    - Firestore documents — persistent cloud storage
    - Firebase Auth — authentication state

  VIEW LAYER (UI):
    - All widget files (*_dashboard.dart, *_screen.dart, *_page.dart)
    - Theme widgets (floating_Action_Button.dart)
    - Custom widgets (stats_widget.dart, floating_menu.dart)

  CONTROLLER LAYER (Business Logic):
    - Services (auth_service.dart, firestore_service.dart, gemini_service.dart)
    - State management within StatefulWidget setState() calls
    - StreamBuilder widgets for reactive data binding

  BACKEND-AS-A-SERVICE (BaaS):
    - Firebase provides the entire backend infrastructure
    - No custom server, API endpoints, or database server is needed
    - Real-time data synchronization via Firestore streams
    - Authentication via Firebase Auth + Google OAuth
    - File storage via Firebase Storage
    - Analytics via Firebase Analytics

5.2 DATA FLOW DIAGRAMS (DFDs)
─────────────────────────────

LEVEL 0 — CONTEXT DIAGRAM:

  [External User] ----> [FestFlow Application] ----> [Firebase Cloud]
                  <----                         <----

  The system has one external entity (User) interacting with the FestFlow
  application, which in turn communicates with Firebase Cloud services.

LEVEL 1 — MAJOR PROCESSES:

  Process 1.0: AUTHENTICATION
    Input:  Google Account credentials
    Output: Authenticated User object + Role assignment
    Store:  Firebase Auth, leader/{email}, users/{email}

  Process 2.0: EVENT MANAGEMENT
    Input:  Event details (title, location, date, etc.)
    Output: Created event with unique code
    Store:  leader/{email}/events/{code}, events/{code}

  Process 3.0: MEMBER MANAGEMENT
    Input:  Member email for invitation
    Output: Member invitation / acceptance
    Store:  events/{code}/member/{email}, users/{email}/events

  Process 4.0: GUEST MANAGEMENT
    Input:  Guest registration + questionnaire answers
    Output: Guest approval status
    Store:  events/{code}/Guest/{email}, events/{code}/guest/{email}

  Process 5.0: SUB-EVENT MANAGEMENT
    Input:  Sub-event details
    Output: Created/updated sub-event
    Store:  events/{code}/sub-events/{id}

  Process 6.0: ANALYTICS AND REPORTING
    Input:  Event statistics from Firestore
    Output: AI-generated report + charts + CSV export
    External: Google Gemini API

  Process 7.0: NOTIFICATION SYSTEM
    Input:  Event actions (guest approval, new member, etc.)
    Output: Push notifications to user feeds
    Store:  users/{email}/notifications

LEVEL 2 — SUB-PROCESS DETAIL (Authentication):

  Process 1.1: Google Sign-In
    -> GoogleSignIn().signIn() -> GoogleSignInAuthentication
    -> GoogleAuthProvider.credential() -> FirebaseAuth.signInWithCredential()

  Process 1.2: Role Resolution
    -> Query users/{email}/events OR leader/{email}
    -> Extract role field -> Route to appropriate dashboard

  Process 1.3: Auto-Login Check
    -> FirebaseAuth.currentUser (cached session)
    -> If exists -> Process 1.2
    -> If null -> Show login screen

5.3 ALGORITHMS
──────────────

ALGORITHM 1: Auto-Login Router (face_page.dart)
  INPUT: None (uses cached Firebase Auth session)
  OUTPUT: Navigation to appropriate dashboard

  BEGIN
    user = FirebaseAuth.currentUser
    IF user == null THEN
      NAVIGATE to HomePage
      RETURN
    END IF

    events = QUERY users/{user.email}/events
    IF events is empty THEN
      NAVIGATE to HomePage
      RETURN
    END IF

    firstEvent = events[0]
    role = firstEvent.role
    eventCode = firstEvent.id
    GlobalState.activeEventCode = eventCode

    SWITCH role:
      CASE "leader":
        IF events/{eventCode}.isApproved == true THEN
          NAVIGATE to LeaderDashboard
        END IF
      CASE "member":
        IF events/{eventCode}.isApproved == true THEN
          NAVIGATE to MemberDashboard
        END IF
      CASE "guest":
        IF firstEvent.isApproved == true THEN
          NAVIGATE to GuestDashboard
        ELSE
          NAVIGATE to AllEventList (waiting)
        END IF
    END SWITCH
  END

ALGORITHM 2: QR Code Join Flow (event_qr_scanner.dart)
  INPUT: Scanned QR code string
  OUTPUT: Navigation to event details or error

  BEGIN
    scannedCode = MobileScanner.onDetect()
    eventDoc = QUERY events/{scannedCode}
    IF eventDoc.exists THEN
      NAVIGATE to AboutEventDetails(eventDoc)
    ELSE
      SHOW error "Invalid event code"
    END IF
  END

ALGORITHM 3: Guest Questionnaire Builder (guest_questions_page.dart)
  INPUT: Leader's question definitions
  OUTPUT: Stored questionnaire in Firestore

  BEGIN
    FOR EACH question added by leader:
      questionData = {
        question: text,
        type: short_answer | paragraph | multiple_choice | checkbox | dropdown,
        options: [list of options] (if type needs them),
        isRequired: boolean,
        order: current_count
      }
      WRITE to events/{code}/guestQuestions/{auto_id}
    END FOR
  END

ALGORITHM 4: Online Presence Tracking (leader_dashboard.dart)
  INPUT: AppLifecycleState changes
  OUTPUT: Firestore online status updates

  BEGIN
    ON app resumed:
      SET users/{email}.isOnline = true
      SET events/{code}/leader/{email}.isOnline = true
      SET local isOnline = true (setState)

    ON app paused OR detached:
      SET users/{email}.isOnline = false
      SET events/{code}/leader/{email}.isOnline = false
      SET local isOnline = false (setState)
  END

9. CODING STANDARDS AND CONVENTIONS
================================================================================

  - Language: Dart 3.10.x with null safety enabled
  - File naming: snake_case (e.g., leader_dashboard.dart)
  - Class naming: PascalCase (e.g., LeaderDashboard)
  - Variable naming: camelCase (e.g., eventCode, isLoading)
  - Private members: Prefixed with underscore (e.g., _menuOpen, _user)
  - Constants: UPPER_SNAKE_CASE for type maps (e.g., questionTypes)
  - Firestore document IDs: User email addresses (not UIDs)
  - Error handling: try-catch blocks with print() for debugging
  - State management: StatefulWidget + setState() (no Provider/Bloc)
  - Navigation: MaterialPageRoute with pushReplacement/pushAndRemoveUntil
  - Async patterns: async/await with Future and StreamBuilder
  - Null safety: Nullable types (String?) with null checks throughout
